# Manual jobs

Managers create a job through six guided stages under **Jobs**: choose a template, configure it, optionally add a schedule, set execution and missed-work policies, review, and explicitly enable. The form is generated from the installed template's validated JSON Schema and built-in UI hints; it does not execute user-supplied scripts, HTML, UI components, or packages. Unsupported schema controls are not rendered as executable content.

The authoring flow saves a disabled draft before activation. Optional schedules are saved against the current job ETag; activation uses the shared server-side validation for the template, configuration, profile, policy, and schedule. A stale ETag keeps the draft visible for correction. **Run now** submits the accepted job command with an idempotency key; a retry after an uncertain response reuses that key. A successful request shows the execution ID and exposes the stop dialog. The timeout policy includes an explicit **No timeout** option rather than assigning that meaning to zero.

Job details provide pause/resume schedule, disable/enable, duplicate, archive, and stop actions to managers. Duplicate creates a disabled copy that must be reviewed before activation. Pause does not replay paused occurrences; manual runs remain available. Disable closes the start gate and releases held retries. Archive prevents future starts and retries while accepted work retains its existing lifecycle. Schedule deletion requires confirmation and leaves the job available for manual execution. The server enforces management permissions and ETags for every command.

The SQL Server form accepts a profile ID, catalog, command kind, SQL text, and parameter metadata. In **Procedure** mode, enter only a procedure name such as `dbo.Job`; add its parameters in the separate parameter list. In **Query** mode, enter the complete statement with `@parameter` placeholders, for example `SELECT * FROM dbo.Orders WHERE ReferenceDate = @Dt_Ref;`, and add a matching parameter row. If invoking a procedure from Query mode, include the complete `EXEC` statement and bind its parameters separately. Configure the manager-only profile under **Settings → SQL profiles**.

Each SQL parameter has one value source: **Fixed value**, **Dynamic value**, **Secret**, or **Send SQL NULL**. SQL NULL sends a database null; it does not mean the parameter is nullable, omitted, or given an empty string. Dynamic sources include the execution reference date, scheduled timestamp, first execution start, execution ID, and idempotency key, with compatible formats and date/time transformations. The idempotency key stays the same across retries of one execution; a separate execution gets a different key, and the destination must cooperate to deduplicate effects. Decimal parameters use **Total digits (precision)** and **Decimal places (scale)**. Blank SQL command timeout means there is no SQL-specific timeout; the form warns when this can wait indefinitely and shows when the overall job timeout still limits it.

Dynamic values can be previewed in the wizard. A preview is an example only: it does not save a fixed value, run the template, resolve secrets, or contact the target. For a scheduled job, the default reference date comes from the original scheduled occurrence in the plan's timezone, even if it runs late or retries after midnight. **Run now** can optionally override the reference date for that execution; leaving it empty uses the accepted request date in the same timezone. This override does not edit the job or its schedule. Within the existing 24-hour deduplication window, a retry with the same request key and override reuses its accepted execution; a different override needs a new request key.

The HTTP form exposes method, URL, bounded response handling, query/header/parameter fields, and secret references. Built-in template version 1.1.0 supports declared dynamic parameter values and preview; query and URL substitutions are encoded for their component. Secret references are logical names; the browser never accepts or displays a password/token value. Profile diagnostics return a safe command status and do not display connection strings or response bodies. Fresh-install catalogs include built-in version 1.1.0; custom templates keep their own versions.

Example values for UI walkthroughs should remain synthetic, such as catalog `WorkerDockTest`, command `SELECT 1`, and URL `https://api.example.test/health`. These values are not a live SQL or HTTP acceptance test. To execute a job locally, follow the [SQL Server tutorial](../tutorials/run-with-sql-server.md), including worker and template limits. The disposable SQL integration-test databases are a separate test setup. Playwright browser tests require the Chromium version installed by the frontend package; discovery can be run without the browser using `npm.cmd --prefix frontend run e2e -- --list`.

Schema-generated forms cover only the closed subset described in [custom templates](add-custom-template.md#validated-catalog-and-schema-subset). See [scheduling](../reference/scheduling.md) and [monitoring](../reference/monitoring.md) for the current behavior.
