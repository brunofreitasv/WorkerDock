# Observability

WorkerDock persists bounded execution and lifecycle events in `workerdock.OperationalEvents` and exposes them through `GET /api/monitoring/executions/{id}/events`. The Read policy applies. Pages default to 50 and cap at 100; the cursor is a stable timestamp/event-ID pair. Unknown executions return 404 and storage failures return 503. The same event table is the authoritative lifecycle stream.

Optional supervisor events use a bounded in-memory channel (128 batches by default). The worker drops on full queue, database failure, or shutdown timeout; none of these conditions changes an execution result. Event writes are idempotent by execution/attempt/source/sequence. Payloads allow only a small event-code and field allowlist, with a 2 KiB JSON cap. `SafeExecutionLog` caps accepted entries and emits a single bounded drop marker. Authentication event storage is not wired because the current host does not expose authoritative authentication outcomes to the application; no synthetic events are emitted.

Handler diagnostics travel over the existing isolated executor pipe as separate frames, while the control listener remains active for Cancel and the terminal result is written after queued diagnostic frames. The executor accepts only allowlisted event codes and fields, redacts known secrets, caps each frame at 4 KiB, caps frames at 256 per attempt, and uses a 32-frame nonblocking queue. The supervisor validates frames again and forwards them through a 64-event nonblocking queue. Invalid, oversized, flooded, backpressured, or unpersistable diagnostics are dropped; the execution result and termination path do not wait on event storage. Executor stdout/stderr remain discarded.

The `WorkerDock` `ActivitySource` emits an attempt span with execution/attempt identity and terminal outcome, exit-confirmation, effects, and persistence status for trace use. The `Meter` uses low-cardinality tags only: allowlisted template ID, outcome, and component; execution and correlation identifiers are excluded from metric tags. Instrumentation uses .NET's built-in APIs; exporters are absent and disabled by default. Hosts may attach listeners/exporters. SQL aggregates are committed before those optional metrics are recorded, and aggregation failures are isolated from job execution.

Metric aggregation claims terminal executions in bounded batches under `ReadCommitted`, using `UPDLOCK,READPAST,READCOMMITTEDLOCK`. The explicit read-committed lock hint keeps the claim compatible with databases using read-committed snapshot isolation while allowing concurrent workers to process separate rows.

The fresh-install baseline creates the event and aggregate tables and grants only `SELECT` on `AuditEvents` to the selected existing runtime database user, preserving its existing `INSERT` permission. It grants no audit `UPDATE` or `DELETE`. Rollback refuses to remove populated diagnostics or aggregates. Runtime processes do not run migrations; deployment applies the manifest-verified baseline.

SQL-backed integration checks require `WORKERDOCK_TEST_SQL`; local SQL verification is blocked when it is unset. The in-memory web adapter does not provide persisted event history.
